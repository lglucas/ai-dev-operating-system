## Como começou

O usuário pediu para clonar o [harness-score](https://github.com/paladini/harness-score) e rodá-lo contra este repositório, com uma condição: poder desinstalar e apagar sem deixar rastro dentro do projeto.

O clone ficou numa pasta irmã, fora do repo (`../_harness-score-sandbox`, commit `1a01406`, v1.7.5), com dependências, build e cache do npm dentro dela. Nada foi instalado globalmente. O scan é só leitura: 36 checagens de sistema de arquivos, sem rede e sem LLM.

Lendo o código das checagens (`packages/cli/src/checks/sensors.ts`), a perda em Sensors tinha uma causa só: o scanner reconhece test runner, linter e formatter por arquivo padrão de ecossistema, e o repo não tinha `package.json`. Os testes existiam e rodavam no CI, chamados direto com `node --test`.

O achado é real mesmo descontando a ferramenta. Um agente que chega no repo não tem `npm test` para descobrir; precisa ler o `ci.yml` ou o README para saber como verificar o próprio trabalho.

## A decisão que moldou o resto: herança

O usuário foi explícito: o OS existe para gerar projetos derivados, e isso não pode ser ignorado. Quem usa "Use this template" recebe a raiz inteira, então um `package.json` aqui é um `package.json` em todo projeto novo.

A alternativa era manter os sensores só no OS e esconder o manifesto dos derivados. Foi descartada: o derivado herda os scripts e os hooks, e portanto também precisa testá-los. O manifesto foi desenhado como **ponto de partida do projeto**, e três coisas seguram isso:

1. `templates/project/CLAUDE.md` e `stack-packs/README.md` mandam mesclar a stack no manifesto, não sobrescrever.
2. `npm test` e `npm run lint` são o contrato. O hook, o CI e o self-test chamam esses dois nomes; o que eles rodam pode mudar.
3. O `os-self-test` avisa, em projeto derivado, enquanto o pacote ainda se chamar `ai-dev-operating-system`.

### Decisões do manifesto

| Decisão | Motivo |
|---|---|
| Sem campo `version` | `CHANGELOG` e `plugin.json` já precisam bater, e há check para isso. Um terceiro lugar divergiria. |
| `"type": "commonjs"` explícito | Sem ele o Biome trata `.js` como módulo ES e reporta o `'use strict'` como redundante. Remover deixaria os scripts em modo não estrito. |
| Biome, e não ESLint + Prettier | Uma dependência faz lint e formatação. Os scripts tinham zero dependências; passar para uma é o menor passo. |
| Versão exata (2.5.15) + lockfile | Regra de ouro 10, e o scanner cobra lockfile assim que existe manifesto. |
| `biome.json` no estilo já usado | Dois espaços, aspas simples, largura 120. Com o padrão do Biome (tabs, aspas duplas) a passada de formatação reescreveria quase todas as linhas de código do repo. |

## O hook de feedback

O README dos hooks dizia que hook é "para o que é irreversível", e por isso só havia hooks sobre segredo. Um hook de lint parece contradizer isso. Não contradiz, porque é outra coisa: roda em `PostToolUse`, depois da ferramenta, e não bloqueia. O README agora separa **gate** de **feedback**.

| Decisão | Motivo |
|---|---|
| Não reescreve o arquivo | Formatar por baixo do agente faz o próximo `Edit` falhar em conteúdo que ele não viu mudar. |
| Silencioso sem o Biome | Clone novo e derivado sem `npm install` se comportam como antes. |
| Só o arquivo editado | O repositório inteiro é trabalho do CI. |
| Escape hatch `AIOS_SKIP_LINT_HOOK=1` | Mesmo padrão dos outros dois hooks. |

O hook ficou ativo no meio desta sessão e pegou um erro real da própria implementação: `checkSensorWiring` declarada no `os-self-test.js` e nunca chamada em `main()`.

## "Sensor ligado" vira verificação

Seguindo a decisão da v0.5.5 de transformar a classe do defeito em check: `scripts/sensor-wiring.js` é o 12º grupo do `os-self-test`. Módulo separado pelo mesmo motivo do `instruction-drift.js` — o self-test já passa de 300 linhas.

A severidade depende do modo. No repo do OS, sensor ausente é erro, porque é o que todo derivado herda. No derivado é aviso: o projeto pode ter ido para outra stack, e check que falha numa escolha legítima acaba desligado.

O check também cobra que o CI rode `npm test` e `npm run lint`. O defeito original era exatamente o inverso — sensor que rodava no CI e não tinha ponto de entrada —, mas a classe é a mesma: sensor pela metade.

## Guardrails encontrados no caminho

Dois hooks da máquina do usuário, de fora deste repo, interferiram, e vale registrar:

- Um gate que exige declarar fatos antes de cada primeira edição de arquivo. Foi atendido arquivo por arquivo.
- Um `config-protection` que bloqueia qualquer edição de `biome.json`. Em vez de contornar, a decisão foi levada ao usuário, que **autorizou gravar esse arquivo pelo shell, uma vez**. Nenhum escape hatch dos hooks deste repo foi usado.

## Ressalvas

- **A nota mede infraestrutura, não qualidade.** O próprio harness-score diz que não avalia se os testes são bons nem se as regras são verdadeiras. L4 aqui significa que as peças existem e estão ligadas.
- **O combinado era L3; saiu L4.** O hook de feedback completou a dimensão de hooks, e isso bastou para o scanner. Os critérios exatos do L4 não foram lidos.
- A ferramenta não publica distribuição de notas. Não há base para dizer "acima da média".

## Em aberto

- Os scripts de detach não renomeiam o pacote. Hoje isso é só um aviso do self-test.
- `npm test` usa um glob sem aspas. No Windows, com Node 20, o `cmd` não expande e o Node ainda não tem glob no `--test`. Funciona no CI (Linux) e no Windows com Node 21 ou mais novo.
- Quando o problema é só formatação, a saída do hook é o diff inteiro, cortado em 4.000 caracteres. Funciona, mas é verboso.
